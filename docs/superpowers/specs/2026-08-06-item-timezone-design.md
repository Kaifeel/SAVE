# 게시물 작성 시각 UTC 서버 대응 설계

## 목표

백엔드가 UTC 시간대의 서버 또는 컨테이너에서 실행되더라도 게시물 작성 시각을 동일한 절대 시각으로 전달해 홈과 상세 화면의 `몇 분 전` 표시가 정확하게 유지되도록 한다.

## 시간대 계약

서비스의 게시물 작성·수정 시각은 `Asia/Seoul`을 명시적으로 사용한다. 서버 운영체제와 JVM의 기본 시간대에는 의존하지 않는다.

데이터베이스의 기존 `timestamp` 열과 `LocalDateTime` 엔티티 필드는 유지한다. 저장된 값은 한국 현지 시각이라는 기존 의미를 보존한다. API 응답에서만 해당 값을 `Asia/Seoul`의 UTC 오프셋과 결합해 `2026-08-06T12:00:00+09:00` 형식으로 직렬화한다.

이 계약에 따라 UTC 서버의 현재 시각이 `03:00Z`인 순간에도 새 게시물에는 한국 현지 시각 `12:00`이 저장되고, 응답은 `12:00+09:00`으로 전달된다. 두 값은 같은 절대 시각을 뜻한다.

## Java 구성 요소

공용 Java 시간 유틸리티는 다음 두 책임만 가진다.

- 서버 기본 시간대와 무관하게 `Asia/Seoul`의 현재 `LocalDateTime`을 생성한다.
- 저장된 한국 현지 `LocalDateTime`을 `+09:00`이 포함된 `OffsetDateTime`으로 변환한다.

유틸리티에는 한국 서비스의 로컬 시각 저장 계약과 UTC 서버 대응 이유를 설명하는 Java 주석을 추가한다. `Item`의 생성·수정 콜백은 이 유틸리티를 사용한다. `ItemResponse`의 `createdAt`과 `updatedAt`은 `OffsetDateTime`으로 반환한다.

## 데이터 및 호환성

데이터베이스 스키마와 마이그레이션은 변경하지 않는다. 기존 한국 로컬 개발 환경에서 생성한 `LocalDateTime` 값을 그대로 한국 시각으로 해석하므로 기존 데이터가 9시간 이동하지 않는다.

프런트의 `Date` 파서는 `+09:00` 오프셋을 포함한 문자열을 절대 시각으로 해석한다. 기존 상대 시간 포매터와 1분 갱신 훅은 변경하지 않는다.

## 오류 및 경계 처리

응답 변환 대상 시각이 `null`이면 변환 결과도 `null`로 유지한다. 엔티티가 정상적으로 저장된 경우 작성·수정 시각은 항상 존재한다.

이 변경은 게시물 작성·수정 시각에만 적용한다. 대여 시작·종료 시각과 다른 도메인의 감사 시각을 전환하는 작업은 별도 범위다.

## 테스트

- Java 시간 유틸리티가 지정된 `LocalDateTime`에 `+09:00` 오프셋을 결합하는지 검증한다.
- JVM 기본 시간대를 UTC로 둔 상황에서도 새 현재 시각이 `Asia/Seoul` 기준인지 검증한다.
- 게시물 API 응답의 `created_at`과 `updated_at`에 `+09:00`이 포함되는지 검증한다.
- 프런트 상대 시간 테스트에서 실제 백엔드 계약과 같은 `+09:00` 입력을 유지한다.
- 백엔드 전체 테스트, 프런트 전체 테스트, ESLint, 프로덕션 빌드를 실행한다.

## 범위 제외

- 데이터베이스 전체를 `Instant` 또는 `timestamptz`로 이전하는 작업
- 대여 예약 시작·종료 시각의 API 계약 변경
- JVM 전역 기본 시간대를 강제로 변경하는 설정
